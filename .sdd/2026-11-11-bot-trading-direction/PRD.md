# Product Requirements Document (PRD)

**Status:** Finalized
**Version:** v1.0
**Owner:** James Hsueh
**Stakeholders:** Engineering

---

## 1. Background & Goal (Why & Goal)

- **Problem Statement:** 合約交易策略今天記著自己的**合約交易模式**（多空反手、只做多、只做空）。同一套買賣判斷想同時拿來做多與做空，就得複製成兩份一模一樣、只差交易模式的交易策略；改一份還得記得改另一份。交易模式其實不是「怎麼判斷」，而是「判斷出來之後怎麼用」，卻被綁在判斷上。另外，機器人每一個結論都只能「送出通知」或「什麼都不說」，擁有者無法依結論種類決定要不要被打擾。
- **Expected Outcome:**
  - 交易策略只回答買入／賣出／持有，不再帶交易模式；一份交易策略可同時被一台做多的機器人與一台做空的機器人引用。
  - 合約機器人自己選**交易方向**，行為（訊息的合約動作、自動下單）與今天用對應交易模式時完全相同。
  - 交易策略回測由送出的人說交易方向；實盤比對從交易本身推得交易方向。
  - 每台機器人可分別開關買入、賣出、持有三種結論的通知。
  - 升級後每台既有機器人的行為不變。
- **Out of Scope:** 逐種結論分別決定自動下單；標的篩選與直接回測策略腳本的交易方向（本來就不讀交易策略）；現貨自動下單；前端畫面與外掛（各自專案）。

---

## 2. User Personas

- **Primary Role(s):** 策略機器人擁有者（一般使用者）。也透過外掛代他操作的助理。
- **Usage Context:** 在網頁或透過外掛設定交易策略、機器人與回測；機器人在背景依觸發間隔跑輪次，經 Telegram 通知擁有者，開著自動下單時在擁有者的幣安帳戶下單。

---

## 3. User Stories & Acceptance Criteria

### US-01 — 交易策略不再帶交易方向 [priority: P0]
**As a** 交易策略擁有者, **I want** 交易策略只負責判斷買入、賣出、持有, **so that** 同一份規則能被不同方向的機器人共用。

```gherkin
Scenario: 建立合約交易策略不提交易方向
  Given 一份合約交易策略，沒有提到交易方向
  When 擁有者建立它
  Then 建立成功
  And 查詢這份交易策略時沒有交易方向這一項

Scenario: 建立時送來交易方向被拒絕
  Given 一份合約交易策略，送來「只做多」
  When 擁有者建立它
  Then 建立被拒絕，並說明交易方向已改由機器人與回測決定

Scenario: 修改時送來交易方向被拒絕
  Given 一份既有的合約交易策略，修改內容中送來「多空反手」
  When 擁有者修改它
  Then 修改被拒絕，並說明交易方向已改由機器人與回測決定
```

### US-02 — 機器人的交易方向決定買入、賣出的意思 [priority: P0]
**As a** 合約機器人擁有者, **I want** 在機器人上選做多、做空或兩者, **so that** 機器人依我要的方向解讀交易策略的結論。

```gherkin
Scenario: 只做多的機器人結論買入
  Given 一台交易方向為「做多」的合約機器人
  When 這一輪結論買入
  Then 輪次訊息的合約動作寫「做多」
  And 開著自動下單時送出開多的委託

Scenario: 只做多的機器人結論賣出
  Given 一台交易方向為「做多」的合約機器人，手上有機器人多單
  When 這一輪結論賣出
  Then 輪次訊息的合約動作寫「平多」
  And 開著自動下單時只平掉多單，不開空

Scenario: 只做空的機器人結論賣出
  Given 一台交易方向為「做空」的合約機器人
  When 這一輪結論賣出
  Then 輪次訊息的合約動作寫「做空」
  And 開著自動下單時送出開空的委託

Scenario: 只做空的機器人結論買入
  Given 一台交易方向為「做空」的合約機器人，手上有機器人空單
  When 這一輪結論買入
  Then 輪次訊息的合約動作寫「平空」
  And 開著自動下單時只平掉空單

Scenario: 兩個方向都選的機器人反手
  Given 一台交易方向為「做多＋做空」的合約機器人，手上有機器人空單
  When 這一輪結論買入
  Then 輪次訊息的合約動作寫「做多」
  And 開著自動下單時先平掉空單再開多

Scenario: 同一份交易策略養兩個方向的機器人
  Given 同一份交易策略被 A 機器人（交易方向「做多」，手上有多單）與 B 機器人（交易方向「做空」）引用
  When 同一輪兩台都結論賣出
  Then A 的合約動作寫「平多」
  And B 的合約動作寫「做空」
```

### US-03 — 設定與修改交易方向 [priority: P0]
**As a** 合約機器人擁有者, **I want** 建立時選方向、之後在安全的時候才能改, **so that** 一台正在用真錢交易的機器人不會被半路改掉方向。

```gherkin
Scenario: 建立時選做多
  Given 一台合約機器人，交易方向選「做多」
  When 擁有者建立它
  Then 建立成功，交易方向為「做多」

Scenario: 建立時沒說交易方向
  Given 一台合約機器人，沒有提到交易方向
  When 擁有者建立它
  Then 建立成功，交易方向為「做多＋做空」

Scenario: 一個方向都沒選
  Given 一台合約機器人，交易方向給了空的清單
  When 擁有者建立它
  Then 建立被拒絕，並說明至少要選一個交易方向

Scenario: 現貨機器人送來交易方向
  Given 一台現貨機器人，交易方向選「做多」
  When 擁有者建立它
  Then 建立被拒絕，並說明現貨機器人沒有交易方向

Scenario: 安全時改方向
  Given 一台已停止、自動下單關著、沒有機器人持倉的合約機器人，交易方向「做多」
  When 擁有者把交易方向改成「做空」
  Then 修改成功，交易方向為「做空」

Scenario: 自動下單開著時改方向
  Given 一台已停止、自動下單開著的合約機器人，交易方向「做多」
  When 擁有者把交易方向改成「做空」
  Then 修改被拒絕，並說明要先關掉自動下單才能改交易方向

Scenario: 還有機器人持倉時改方向
  Given 一台已停止、自動下單關著的合約機器人，監聽標的 BTCUSDT 還有機器人持倉
  When 擁有者改交易方向
  Then 修改被拒絕，並說出 BTCUSDT 還有機器人持倉

Scenario: 自動下單開著但沒有改方向
  Given 一台已停止、自動下單開著的合約機器人
  When 擁有者只改觸發間隔，交易方向不變
  Then 修改成功

Scenario: 執行中改方向
  Given 一台執行中的合約機器人
  When 擁有者改交易方向
  Then 修改被拒絕，並說明要先停止機器人
```

### US-04 — 每種結論的通知 [priority: P1]
**As a** 機器人擁有者, **I want** 分別決定買入、賣出、持有要不要通知我, **so that** 我只在關心的結論被打擾。

```gherkin
Scenario: 買入通知開著
  Given 一台買入通知開著的機器人，監聽標的沒有上一次送出的信號
  When 這一輪結論買入
  Then 寄出一則買入的輪次訊息

Scenario: 買入通知關掉時照樣決定與下單
  Given 一台買入通知關著、自動下單開著的合約機器人，監聽標的沒有上一次送出的信號
  When 這一輪結論買入
  Then 不寄輪次訊息
  And 照樣送出自動下單委託
  And 上一次送出的信號記為買入

Scenario: 靜默決定的信號照樣擋掉重複
  Given 一台買入通知關著的機器人，上一次送出的信號是買入
  When 這一輪再結論買入
  Then 視為重複，不寄訊息也不下單

Scenario: 回到持有時通知一次
  Given 一台持有通知開著的機器人，監聽標的前一個有意見的結論是買入
  When 這一輪結論持有
  Then 寄出一則「回到持有」的訊息，沒有建議部位
  And 不送出任何自動下單委託

Scenario: 連續持有不重複通知
  Given 一台持有通知開著的機器人，監聽標的前一個有意見的結論是持有
  When 這一輪再結論持有
  Then 不寄訊息

Scenario: 衝突不打斷連續的持有
  Given 一台持有通知開著的機器人，監聽標的前一個有意見的結論是持有
  When 這一輪結論衝突，下一輪又結論持有
  Then 兩輪都不寄訊息

Scenario: 剛啟動的第一個結論是持有
  Given 一台持有通知開著、剛啟動的機器人
  When 第一輪結論持有
  Then 寄出一則「回到持有」的訊息

Scenario: 持有通知關著
  Given 一台持有通知關著的機器人，監聽標的前一個有意見的結論是賣出
  When 這一輪結論持有
  Then 不寄訊息

Scenario: 持有不改變上一次送出的信號
  Given 一台持有通知開著的機器人，上一次送出的信號是買入
  When 依序結論買入、持有、買入
  Then 持有那一輪寄出「回到持有」
  And 第二個買入視為重複，不寄訊息也不下單

Scenario: 三個通知都關
  Given 一台買入、賣出、持有通知都關著的機器人
  When 擁有者啟動它，第一輪結論買入
  Then 寄出「已啟動」
  And 買入那一輪不寄訊息

Scenario: 新機器人的預設通知
  Given 一台建立時沒有提到通知的機器人
  When 擁有者建立它
  Then 買入通知開、賣出通知開、持有通知關

Scenario: 執行中改通知
  Given 一台執行中的機器人
  When 擁有者關掉買入通知
  Then 修改被拒絕，並說明要先停止機器人
```

### US-05 — 交易策略回測的交易方向 [priority: P0]
**As a** 交易策略擁有者, **I want** 回測時自己說要測哪個方向, **so that** 同一份交易策略能分別看做多與做空的成績。

```gherkin
Scenario: 回測合約交易策略只做空
  Given 一份合約交易策略，回測時說交易方向「做空」
  When 擁有者送出回測
  Then 照只做空重演
  And 成績單記著交易方向「做空」

Scenario: 回測時沒說交易方向
  Given 一份合約交易策略，回測時沒有提到交易方向
  When 擁有者送出回測
  Then 照多空反手重演
  And 成績單記著交易方向「做多＋做空」

Scenario: 現貨交易策略回測送來交易方向
  Given 一份現貨交易策略，回測時說交易方向「做多」
  When 擁有者送出回測
  Then 回測被拒絕，並說明現貨重演只做現貨
```

### US-06 — 實盤比對從交易本身推得交易方向 [priority: P1]
**As a** 交易日誌使用者, **I want** 比對時依我實際做的方向重演, **so that** 比對結果反映我真正的交易。

```gherkin
Scenario: 比對的交易全是多單
  Given 拿來比對的合約交易全是多單
  When 擁有者要求實盤與回測比對
  Then 回測照只做多重演

Scenario: 比對的交易全是空單
  Given 拿來比對的合約交易全是空單
  When 擁有者要求實盤與回測比對
  Then 回測照只做空重演

Scenario: 比對的交易多空都有
  Given 拿來比對的合約交易有多單也有空單
  When 擁有者要求實盤與回測比對
  Then 回測照多空反手重演
```

### US-07 — 既有資料升級 [priority: P0]
**As a** 既有機器人擁有者, **I want** 升級後機器人照原樣運作, **so that** 我不必重新設定任何東西。

```gherkin
Scenario: 用只做多交易策略的合約機器人
  Given 一台合約機器人，它的交易策略交易模式是只做多
  When 系統升級
  Then 機器人交易方向為「做多」
  And 買入通知開、賣出通知開、持有通知關

Scenario: 用只做空交易策略的合約機器人
  Given 一台合約機器人，它的交易策略交易模式是只做空
  When 系統升級
  Then 機器人交易方向為「做空」

Scenario: 交易策略交易模式沒填
  Given 一台合約機器人，它的交易策略交易模式沒填
  When 系統升級
  Then 機器人交易方向為「做多＋做空」

Scenario: 現貨機器人
  Given 一台現貨機器人
  When 系統升級
  Then 機器人沒有交易方向
  And 買入通知開、賣出通知開、持有通知關

Scenario: 升級重做不覆蓋擁有者的修改
  Given 已升級的合約機器人，擁有者之後把交易方向改成「做空」
  When 升級再做一次
  Then 機器人交易方向仍為「做空」

Scenario: 已跑完的回測輪次保留歷史
  Given 一筆已跑完的回測輪次記著只做多
  When 系統升級
  Then 這筆回測輪次照舊記著只做多
```

## 4. Business Flow & Logic

- **Core Business Rules:**
  - 交易方向 → 合約交易模式：只有做多＝只做多；只有做空＝只做空；兩者＝多空反手。合約動作、自動下單目標部位的推得方式與今天各交易模式完全相同，只是來源從交易策略換成機器人（或回測請求、或比對的交易）。
  - 修改交易方向的檢查順序：須已停止 → 自動下單須關著 → 每個監聽標的都沒有機器人持倉與未完成的自動下單委託。交易方向沒有變時不做後兩項檢查。
  - 「上一次送出的信號」改稱「決定要送」的語意：買入／賣出通知關著時照樣更新它。
  - 「前一個有意見的結論」：每個監聽標的記著它最近一個買入、賣出或持有的結論（衝突不記）；啟動時清空。持有通知只在本輪結論持有且前一個有意見的結論不是持有時送。
  - 「回到持有」的訊息與輪次訊息一樣受**送達期限**約束；它寄不出去不影響任何信號狀態。
- **Edge Cases:**
  - 舊的外掛或畫面仍在交易策略上送交易模式 → 被拒絕，訊息說明去處（不默默吞掉）。
  - 機器人的交易策略被刪除 → 照舊不可能（被引用的交易策略不能刪）。
  - 升級時合約機器人找不到它的交易策略（理論上不會發生）→ 視為交易模式沒填，方向為兩者。

## 6. Non-Functional Requirements

- **Security:** 交易方向的修改受「自動下單開著不得改」保護；開關自動下單仍然只能在網頁上進行，因此外掛無法改變一台真錢機器人的方向。
- **Compatibility:** 升級可重複執行、結果不變。

---

## 7. Dependencies & Risks

- **Dependencies:** 前端與外掛須同步改版（交易策略不再送交易模式；機器人送交易方向與通知；回測送交易方向）。舊版前端或外掛在升級後送交易模式會被拒絕。
- **Known Risks:** 「上一次送出的信號」語意改變，靜默決定的信號若沒照樣更新，會造成每輪重複下單——驗收情境已涵蓋。
