## 1. Background & Goal (Why & Goal)

- **Problem Statement:**
  到今天為止，任何人只要知道這個操作台在哪，填一個電子郵件與一組密碼，
  就是一位貨真價實的使用者——**建完立刻什麼都能用**。
  這是一台會替人算錢、會替人發訊息、會替人跑機器人的操作台，
  而它對「誰可以進來」完全沒有意見。

- **Expected Outcome:**
  「成為使用者」與「能夠使用」之間多了一道人工關卡。可驗證的結果有六項：
  1. 新建立的使用者**一律是待開通**，且建立當下**無從指定**成已開通。
  2. 建立成功的那一刻，他當場拿到**開通指示**：寄去哪、主旨怎麼寫。
  3. 待開通的人**登入得進來、問得出自己是誰、續用得了、登出得掉**。
  4. 待開通的人做**其餘每一件需要知道他是誰的事**，一律被擋，並再拿到同一段開通指示。
  5. 「尚未開通」與「請先登入」是**兩句不同的話**，且呼叫端**分辨得出來**。
  6. 管理者在系統之外把他改成已開通之後，他**不必重新登入**，手上那份身分證明立刻就通。

- **Out of Scope:**
  - **系統代寄那封申請信。** 信由使用者自己寄。
  - **後台審核畫面、開通用的操作、管理者身分。** 放行在系統之外直接改資料。
  - **把已開通再改回待開通（停權）。** 這道關卡只管第一次放不放進來。
  - **記住誰寄過申請信、申請到哪一步。** 系統不追蹤。
  - **今天不需要知道你是誰就能用的那些事**（查交易標的、查 K 線、觀察清單）。
    它們對任何人都開著，沒有一個「你」可以拿來比對開通狀態；要擋得先讓它們需要登入，那是另一件事。

## 2. User Personas

- **Primary Role(s):**
  - **使用者**——剛建立帳號、正在等放行的那個人，以及已經被放行、日常在用的那個人。
  - **管理者**——**不是系統裡的一種身分**。他是拿得到資料庫的那個人（實務上就是這台操作台的主人），
    放行動作完全發生在系統之外。
- **Usage Context:**
  使用者在瀏覽器上建立帳號，讀到指示後**離開這個系統、去開自己的信箱**寄一封信，
  然後回來等。等的期間他會反覆重整、反覆登入，想知道放行了沒——
  所以「他看得到自己現在是待開通」比什麼都重要。
  被放行的那一刻**沒有任何通知**，他是自己重整時發現的。

## 3. User Stories & Acceptance Criteria

### US-01 — 建立帳號時就知道自己還不能用，也知道該怎麼辦 [priority: P0]

**As a** 剛建立帳號的使用者，**I want** 在建立成功的當下就知道我還不能用、以及要寄信去哪，
**so that** 我不會以為自己已經可以開始用，然後在第一個動作被擋時完全不知道發生什麼事。

```gherkin
Scenario: 新建立的使用者一律待開通，並當場拿到開通指示
  Given 系統沒有「alice@example.com」這位使用者
  And 開通申請信箱是「james.afternoon.dev@gmail.com」
  When 他用「alice@example.com」與一組合法的密碼建立使用者
  Then 建立成功
  And 回覆說明他的帳號開通狀態是「待開通」
  And 回覆說明要寄信到「james.afternoon.dev@gmail.com」
  And 回覆說明信的主旨要寫「go-trading 開通申請：alice@example.com」

Scenario: 主旨裡寫的是留存下來的電子郵件，不是他打進去的拼法
  Given 系統沒有「alice@example.com」這位使用者
  When 他用「　Alice@Example.com　」與一組合法的密碼建立使用者
  Then 建立成功
  And 回覆說明信的主旨要寫「go-trading 開通申請：alice@example.com」

Scenario: 建立當下指定不了自己是已開通
  Given 系統沒有「alice@example.com」這位使用者
  When 他建立使用者，並試圖一併指定自己是「已開通」
  Then 建立成功
  And 建立出來的這位使用者的帳號開通狀態是「待開通」

Scenario: 這道關卡上線之前就存在的使用者也是待開通
  Given 「old@example.com」是這道關卡上線之前就建立的使用者
  When 查看他的帳號開通狀態
  Then 他的帳號開通狀態是「待開通」
```

### US-02 — 等放行的期間，我進得來也看得到自己的處境 [priority: P0]

**As a** 待開通的使用者，**I want** 登入得進來、問得出自己是誰、而且看得到自己還在等，
**so that** 我有辦法自己確認放行了沒，不必盲等也不必去問人。

```gherkin
Scenario: 待開通不影響登入
  Given 「alice@example.com」是待開通的使用者，密碼是「correct horse」
  When 他以「alice@example.com」與「correct horse」登入
  Then 登入成功，拿到他的身分證明

Scenario: 待開通的人問得出自己是誰，並且看得到自己還在等
  Given 「alice@example.com」是待開通的使用者，且已經登入
  When 他問「我是誰」
  Then 回覆他的使用者識別碼與「alice@example.com」
  And 回覆說明他的帳號開通狀態是「待開通」
  And 回覆附上開通指示：寄到「james.afternoon.dev@gmail.com」、主旨「go-trading 開通申請：alice@example.com」

Scenario: 已開通的人問得出自己已經放行
  Given 「alice@example.com」是已開通的使用者，且已經登入
  When 他問「我是誰」
  Then 回覆他的使用者識別碼與「alice@example.com」
  And 回覆說明他的帳號開通狀態是「已開通」

Scenario: 待開通的人續用得了自己的身分證明
  Given 「alice@example.com」是待開通的使用者，且持有一份還沒作廢的續用憑證
  When 他要求續用
  Then 續用成功，換到一對全新的憑證

Scenario: 待開通的人登得出去
  Given 「alice@example.com」是待開通的使用者，且已經登入
  When 他要求登出
  Then 登出成功
```

### US-03 — 沒放行之前，我什麼都做不了，而且看得懂為什麼 [priority: P0]

**As a** 這台操作台的主人，**I want** 待開通的人做不了任何一件需要知道他是誰的事，
**so that** 陌生人建了帳號也動不了這台會替人算錢、發訊息、跑機器人的機器。

```gherkin
Scenario: 已開通的人照常做事
  Given 「alice@example.com」是已開通的使用者，且已經登入
  When 他建立一支策略腳本
  Then 建立成功

Scenario: 待開通的人被擋下，並拿到同一段開通指示
  Given 「alice@example.com」是待開通的使用者，且已經登入
  When 他建立一支策略腳本
  Then 建立被拒絕，什麼都沒有被建立
  And 拒絕的理由是他的帳號尚未開通
  And 回覆附上開通指示：寄到「james.afternoon.dev@gmail.com」、主旨「go-trading 開通申請：alice@example.com」

Scenario: 被擋下的理由不會被誤認成別的失敗
  Given 「alice@example.com」是待開通的使用者，且已經登入，目前的密碼是「correct horse」
  When 他以目前的密碼「correct horse」與新的密碼「battery staple」要求變更密碼
  Then 變更被拒絕，理由是他的帳號尚未開通
  And 拒絕的理由不是「目前的密碼不正確」
  And 他的密碼仍然是「correct horse」

Scenario: 問助手同樣被擋
  Given 「alice@example.com」是待開通的使用者，且已經登入
  When 他問助手一個問題
  Then 提問被拒絕，理由是他的帳號尚未開通
  And 回覆附上開通指示

Scenario: 「尚未開通」與「請先登入」是兩句不同的話
  Given 一個請求完全沒有帶著任何身分
  When 要求建立一支策略腳本
  Then 建立被拒絕，理由是要先登入
  And 拒絕的理由不是「帳號尚未開通」

Scenario: 呼叫端分辨得出這兩種拒絕
  Given 「alice@example.com」是待開通的使用者，且已經登入
  When 他建立一支策略腳本
  Then 被拒絕的呼叫端不必讀那段給人看的說明文字，就分辨得出這是「尚未開通」而不是「請先登入」
```

### US-04 — 放行之後立刻就能用，不必重登 [priority: P0]

**As a** 剛被放行的使用者，**I want** 不必重新登入就能開始用，
**so that** 我重整一下畫面就發現自己進得去了，而不是又被丟回登入畫面。

```gherkin
Scenario: 被放行之後手上那份身分證明立刻就通
  Given 「alice@example.com」是待開通的使用者，且已經登入
  And 他剛剛才因為尚未開通被擋下一次
  When 管理者在系統之外把他改成「已開通」
  And 他用同一份身分證明再建立一次策略腳本，中間沒有重新登入
  Then 建立成功

Scenario: 被放行之後問「我是誰」看得到自己已經放行
  Given 「alice@example.com」是待開通的使用者，且已經登入
  When 管理者在系統之外把他改成「已開通」
  And 他用同一份身分證明問「我是誰」，中間沒有重新登入
  Then 回覆說明他的帳號開通狀態是「已開通」
  And 回覆不再附上開通指示
```

### US-05 — 放行只發生在系統之外 [priority: P1]

**As a** 這台操作台的主人，**I want** 系統本身完全沒有「開通」這個操作，
**so that** 沒有任何一條路能讓人替自己或替別人放行。

```gherkin
Scenario: 使用者放行不了自己
  Given 「alice@example.com」是待開通的使用者，且已經登入
  When 他尋找一個能把自己改成「已開通」的操作
  Then 系統沒有這件事可以做
  And 他的帳號開通狀態仍然是「待開通」

Scenario: 使用者放行不了別人
  Given 「bob@example.com」是已開通的使用者，且已經登入
  And 「alice@example.com」是待開通的使用者
  When 他尋找一個能把「alice@example.com」改成「已開通」的操作
  Then 系統沒有這件事可以做
  And 「alice@example.com」的帳號開通狀態仍然是「待開通」
```

## 4. Business Flow & Edge Cases

**Happy path**

1. 一個人用電子郵件與密碼建立使用者 → 建立成功，狀態**待開通**，當場拿到**開通指示**。
2. 他離開系統，用自己的信箱寄一封信到**開通申請信箱**，主旨照**開通申請主旨**寫。
3. 管理者看到信，在系統之外把那一位改成**已開通**。
4. 他重整畫面 → 問「我是誰」得到**已開通** → 開始正常使用，**不必重新登入**。

**Edge cases**

| 情況 | 行為 |
| :--- | :--- |
| 他還沒寄信就開始用 | 一律被擋，並再拿到一次開通指示 |
| 他寄了信但管理者還沒看 | 一律被擋。**系統完全不知道他寄過**，也不會催任何人 |
| 他在等的期間身分證明過期 | 續用照常成功，不必重登 |
| 他在等的期間登出再登入 | 照常成功，狀態仍是待開通 |
| 他被擋下之後**沒有重整**就被放行了 | 下一個動作就會通——狀態每次都重新去看 |
| 管理者自己也是待開通 | **沒有人進得去**。見 Section 7 的風險與對策 |
| 完全沒登入的人來做事 | 得到「請先登入」，**不是**「尚未開通」 |
| 他去做今天不需要知道他是誰的事 | 不受這道關卡影響——那裡沒有一個「他」可以拿來比對 |

**State transitions**

```
（建立）──▶ 待開通 ──（管理者在系統之外改資料）──▶ 已開通
                                                    │
                                              （沒有回頭路）
```

## 5. UI/UX

- 沒有既有設計稿。
- **建立帳號成功之後**：畫面要直接顯示開通指示——信箱、主旨、以及一鍵開信的方式。
  主旨必須**可以原封不動複製**，因為它是管理者辨認申請人的唯一依據，打錯一個字就認不出來。
- **待開通的人登入之後**：一律導到一個**等待開通**的畫面，**跳不掉**——
  他從任何一個網址進來都會被帶回這裡。畫面上有同一段開通指示，以及一個「重新檢查」的動作。
- **被放行之後**：他重整或按「重新檢查」就進得去，不出現任何「請重新登入」。
- **錯誤狀態**：待開通的人若因為任何原因看到一則失敗訊息，訊息必須說的是「尚未開通」，
  不能是「請重新登入」——照著做也不會有任何改變的指示，比沒有指示更糟。
- 前端的畫面細節另由前端自己的切片決定，本文件只規定「不容跳過」與「訊息不得混淆」兩條。

## 6. Non-Functional Requirements

- **一致性**：開通狀態**每一次請求都重新去看**，不快取、不寫進身分證明。
  放行的效果因此是立即的，代價是每次都多讀一次——這台操作台只服務個位數的人，這個代價不存在。
- **安全性**：
  - 開通狀態**無從由外部指定**，不論是建立時、變更時或任何一條路。
  - 開通指示裡**只包含申請人自己的電子郵件**，不洩漏任何其他使用者的存在。
  - 被擋下的請求**什麼都不改變**——不留下任何紀錄、不改任何資料。
- **設定**：開通申請信箱與開通申請主旨前綴**由設定給入**，不寫死。
  兩者**都有預設值**（信箱預設為 `james.afternoon.dev@gmail.com`、前綴預設為 `go-trading 開通申請`），
  沒設定時照常運作——這不是鑰匙，猜得到也不會有事，缺了它而讓整個系統起不來才是壞事。
- **相容性**：這道關卡**不改變任何既有功能對已開通使用者的行為**。已開通的人看到的一切與今天完全相同。

## 7. Dependencies & Risks

| 項目 | 說明 | 對策 |
| :--- | :--- | :--- |
| **上線那一刻所有人被關在門外** | 包含管理者自己。沒有人進得去 | 放行的第一件事是**把自己打開**。這件事必須寫進交付說明，不能靠記得 |
| **沒有人會被通知有人在等** | 信寄到一個信箱，沒人看就沒人知道 | 接受。這是不寄信、不做後台換來的代價，明講而不假裝沒有 |
| **申請信可能進垃圾桶或根本沒寄** | 系統完全不知情 | 接受。使用者唯一的自救方式是再寄一次 |
| **今天不需要登入的那些事擋不住** | 查交易標的、查 K 線、觀察清單對任何人都開著 | 本切片**不處理**。要擋得先讓它們需要登入，另開切片 |
| **外部相依** | 無。不接任何寄信服務、不接任何第三方 | — |
