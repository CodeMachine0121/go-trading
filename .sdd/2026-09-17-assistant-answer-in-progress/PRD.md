## 1. Background & Goal (Why & Goal)

### Problem Statement

一次回答在寫的時候，只活在那一條 HTTP 連線上。連線是使用者關得掉的東西，
而一次回答不該是。

助手現在會拼交易策略、會自己重演、會不滿意再改一次——一次回答可能好幾分鐘。
於是三件事同時變成問題：重新整理那一次就沒了、關掉分頁那一次被砍掉、
一條開著好幾分鐘的請求本來就會在某一層被掐掉。

### Expected Outcome

- 一次回答**一被提出就留下紀錄**，狀態是進行中，並立刻交還給使用者。
- 真正去問助手的那段**跑在連線之外**，斷線照樣跑完。
- 讀一段對話時，**進行中與失敗的那幾次也讀得到**，畫面重整之後看到同一件事。
- 同一段對話一次只跑一個。
- 系統啟動時把殘留的進行中一律收成失敗。

### Out of Scope

- 主動推播、取消進行中的回答、跨系統排隊、串流吐字。

---

## 2. User Personas

**Primary Role:** 已登入的使用者。

**Usage Context:** 他送出一句之後**可能離開畫面**——去泡咖啡、切到別的分頁、
關掉瀏覽器晚點再回來。這是這個切片存在的全部理由：
在他不在場的那幾分鐘裡，系統要替他記得發生過什麼。

## 3. User Stories & Acceptance Criteria

### US-01 — 一次回答一被提出就留下來 [priority: P0]

**As a** 使用者，**I want** 送出之後馬上知道系統收下了，
**so that** 我不必盯著一個轉圈圈猜它有沒有送出去。

```gherkin
Scenario: 送出之後馬上拿到回應
  Given 我問了一句
  When 助手還在查
  Then 我馬上拿到這一次回答的識別碼
  And 它的狀態是進行中

Scenario: 助手講完話就轉成已回答
  Given 有一次回答正在進行中
  When 助手講完話
  Then 那一次轉成已回答
  And 答案、用量與查了幾次都寫上去了

Scenario: 助手不可用就轉成失敗
  Given 有一次回答正在進行中
  When 助手不可用
  Then 那一次轉成失敗
  And 它說得出原因
  And 它的用量不計入今日
```

### US-02 — 被擋下來的提問什麼都不留 [priority: P0]

**As a** 使用者，**I want** 根本沒送出去的提問不要在對話裡留下半截，
**so that** 對話裡的每一則都真的發生過。

```gherkin
Scenario: 空白的提問
  Given 我送出一句沒有內容的
  Then 直接被拒絕
  And 對話裡什麼都沒有留下,連進行中都沒有

Scenario: 今日額度用完
  Given 我今天的額度已經用完
  When 我送出一句
  Then 直接被拒絕
  And 什麼都沒有留下

Scenario: 接到別人的對話上
  Given 另一位使用者有一段對話
  When 我把問題接到那一段上
  Then 我拿到「找不到」
  And 什麼都沒有留下
```

### US-03 — 連線斷了它照樣跑完 [priority: P0]

**As a** 使用者，**I want** 關掉分頁不會把助手正在做的事砍掉，
**so that** 它已經幫我拼好的兩支腳本不會白做。

```gherkin
Scenario: 關掉分頁之後照樣跑完
  Given 助手正在查第三輪
  When 我關掉分頁
  Then 它照樣跑完
  And 那一次轉成已回答

Scenario: 回來就看得到
  Given 承上
  When 我重新打開並讀那段對話
  Then 我看得到完整的答案
```

### US-04 — 重新整理之後看得到同一件事 [priority: P0]

**As a** 使用者，**I want** 重整之後還看得到它在跑，
**so that** 我不會以為沒送出去而再問一次、付第二次錢。

```gherkin
Scenario: 進行中的那一次讀得到
  Given 有一次回答正在進行中
  When 我讀那段對話
  Then 那一次在裡面
  And 問句在、答案還沒有、狀態是進行中

Scenario: 失敗的那一次也讀得到
  Given 有一次回答失敗了
  When 我讀那段對話
  Then 那一次在裡面,狀態是失敗
  And 它說得出原因

Scenario: 混在一起時依時間排好
  Given 一段對話裡有三次已回答、一次進行中
  When 我讀它
  Then 四次都在,依時間由早到晚
```

### US-05 — 同一段對話一次只跑一個 [priority: P0]

**As a** 使用者，**I want** 前一次還在跑的時候送不出第二句，
**so that** 同一段對話的來龍去脈永遠說得清楚。

```gherkin
Scenario: 前一次還在跑
  Given 那段對話上有一次回答還在進行中
  When 我再送一句
  Then 被拒絕
  And 它說明前一次還在跑

Scenario: 前一次剛回答完
  Given 那段對話上前一次剛轉成已回答
  When 我再送一句
  Then 送得出去

Scenario: 前一次失敗了不擋路
  Given 那段對話上前一次轉成失敗
  When 我再送一句
  Then 送得出去
```

### US-06 — 重啟時把殘留的收乾淨 [priority: P0]

**As a** 使用者，**I want** 系統重啟不要留下永遠轉不完的圈，
**so that** 畫面上看到的狀態都是真的。

```gherkin
Scenario: 重啟時殘留的轉成失敗
  Given 系統在一次回答進行中時被關掉
  When 它重新啟動
  Then 那一次轉成失敗
  And 原因寫著被重新啟動中斷

Scenario: 重啟之後讀得到那次失敗
  Given 承上
  When 我讀那段對話
  Then 我看得到那一次失敗了,而不是一個永遠在跑的圈
```

## 4. Business Flow & Logic

### 一次提問

```
POST 提問
  ├─ 提問空白？              → 拒絕，什麼都不留
  ├─ 今日額度用完？          → 拒絕，什麼都不留
  ├─ 指名的對話不是自己的？  → 找不到，什麼都不留
  ├─ 那段對話上還有進行中的？→ 拒絕，說明前一次還在跑
  │
  ├─ 沒指名對話就開一段新的
  ├─ 留下一次回答：狀態＝進行中，問句已寫、答案還沒有
  └─ 立刻回覆｛對話識別碼, 回答識別碼, 進行中｝
        │
        └─（連線之外）驅動助手來回查詢
              ├─ 講完話 → 轉成已回答，補上答案、用量、查了幾次
              └─ 出錯   → 轉成失敗，補上原因，用量不計
```

### Core Business Rules

| # | Rule |
|---|------|
| BR-1 | 一次回答有三種狀態：**進行中／已回答／失敗**，且只有這三種 |
| BR-2 | 進入點的三道檢查（空白、額度、對話歸屬）**通過之後**才留下紀錄；沒通過什麼都不留 |
| BR-3 | 驅動助手那段**不綁在請求的生命週期上**，連線斷了照樣跑完 |
| BR-4 | 失敗的那一次**留下紀錄並說得出原因**，但**用量不計入今日** |
| BR-5 | 讀一段對話時三種狀態都讀得到，依時間由早到晚 |
| BR-6 | 一段對話同時最多一次進行中；已有就拒絕新的。**這是資料庫做得到的事，不只是一道檢查**——問與寫是兩個動作，同時抵達的兩個請求會雙雙讀到「沒有東西在寫」 |
| BR-7 | 啟動時把所有殘留的進行中轉成失敗，原因為「被重新啟動中斷」 |

### 為什麼失敗現在要留下來

原本的規則是「不可用即回覆稍後再試，該次問答整個不留下」，理由是
「一次沒有答案的問答不該在對話裡留下半截」。那條規則成立的前提是
**使用者正看著畫面**——送出、失敗、看到錯誤、重打，幾秒內連續發生。

一次回答變成好幾分鐘之後前提就沒了。他人不在，回來時要能自己分辨
「我沒送出去」「送了但失敗了」「送了還在跑」。留下一筆寫著失敗的紀錄，
正是原本那條規則想達成的誠實，只是換了一個他還在場的表達方式。

### 為什麼不另外記一份「誰正在跑」

在記憶體裡存一份名單會與那筆紀錄講出兩種話，而且系統一重啟名單就沒了、
紀錄卻還在。讓那筆紀錄當唯一的真相，重啟時掃一次，兩者永遠不會不同步。

### Edge Cases

| 情境 | 行為 |
|------|------|
| 一次回答跑到一半系統被關掉 | 紀錄停在進行中，下次啟動時收成失敗 |
| 寫那一次回答的過程中壞在沒人想過的地方 | **那一次轉成失敗**，說一句「請再問一次」，行程照常活著。一次回答離開請求之後，HTTP 層那道接住例外的防護就管不到它了——不自己接住的話，一次意外會帶走整個系統：API、背景工作，以及當下每一個正在寫的回答 |
| 兩個提問同時抵達同一段對話 | 一個成功，另一個拿到與「前一次還在跑」**一字不差**的那句話 |
| 助手回了一段空白的答案 | 照既有規則處理；狀態仍轉成已回答 |
| 進行中的那一次還沒有用量 | 用量是 0，今日額度看不到它——額度本來就是事後結算 |
| 使用者在別的分頁同時讀那段對話 | 讀得到進行中的那一次 |
| 同一個人開兩段不同的對話各跑一次 | 都可以——限制是「同一段對話」，不是「同一個人」 |

## 5. UI/UX Design & Interaction

後端只負責讓狀態讀得到。畫面怎麼呈現在前端自己的切片。

回應形狀的變化：
- 提問的回應由「一則答案」變成「一次回答的識別碼與狀態」。
- 讀一段對話時，每一則助手訊息多帶**狀態**，失敗的多帶**原因**。

---

## 6. Non-Functional Requirements

- 提問的回應要**即時**（不等助手），使用者按下去就有反應。
- 畫面以**定時回來問**得知它跑完了；不加長連線。
- 一次回答跑在連線之外，但仍受助手本身的逾時約束（每一趟兩分鐘）。

## 7. Dependencies & Risks

| 項目 | 說明 |
|------|------|
| 依賴 | 對話與一次回答的持久化（既有）、助手查詢驅動（既有） |
| 風險 | 一次回答的資料表多兩欄，既有列要有合理的預設——既有列一律視為已回答 |
| 風險 | 改掉了「失敗不留存」這條既有規則，UL-MAP 要同步更新 |
