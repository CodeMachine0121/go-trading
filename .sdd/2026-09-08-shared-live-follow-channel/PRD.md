## 1. Background & Goal (Why & Goal)

- **Problem Statement:**
  即時跟盤目前是**一檔交易標的開一條即時通道**。台股的行情來源不是這樣賣的：它的方案同時限制兩件事——**同時能開幾條通道**，以及**一條通道能跟幾檔**。目前的方案只允許**一條**通道，但一條通道可以跟**五檔**。

  系統把「同時跟盤上限五檔」誤讀成「可以開五條通道」，於是盤中同時開了四條，超出方案允許的一條。實際觀察到的後果是：通道彼此打架，連上就被踢、被踢就重連，每秒數次；四檔台股沒有一檔拿得到穩定的即時更新，而且持續騷擾行情來源。

- **Expected Outcome:**
  1. 一個限量市場的整份跟盤名單**共用一條即時通道**，通道數不再隨名單長度增加。
  2. 台股在盤中**只開一條**通道，穩定跟住名單上的每一檔，不再出現連上就被踢的循環。
  3. **同時跟盤上限**由方案的兩個真實數字相乘得出，人再也填不出一個方案不允許的值。
  4. 觀看者看到的內容一個字都不變。

- **Out of Scope:**
  - **改變跟盤名單的挑選規則。** 仍是「登錄最早的那幾檔」。
  - **在不中斷通道的情況下增減訂閱。** 行情來源支援單獨取消訂閱，但那會讓通道帶著「目前訂了哪些」的狀態；名單改變本來就不頻繁，本次一律重建通道。
  - **加密貨幣改為共用通道。** 它的行情來源一條通道只跟一檔且不限條數，改了沒有好處。
  - **多條通道的名單分配策略。** 目前唯一的限量市場只允許一條通道；真的有方案給兩條以上時再決定怎麼分。
  - **升級行情來源方案。** 本次是讓系統符合現有方案。

## 2. User Personas

- **Primary Role(s):**
  - **交易研究者**（本系統唯一的使用者）：盤中看某一檔台股的即時走勢。
  - **系統本身**：決定跟盤名單、開關即時通道、在中斷後重新跟上。這些都在無人看顧時發生。

- **Usage Context:**
  台股交易時段內持續運作。名單改變只發生在觀察清單被改動時；通道中斷由行情來源那一端決定，隨時可能發生。

## 3. User Stories & Acceptance Criteria

### US-01 — 同時跟盤上限由方案的兩個數字推導 [priority: P0]

**As a** 交易研究者，**I want** 同時跟盤上限直接反映行情來源方案的真實限制，**so that** 我不會設出一個方案不允許的值，然後在盤中才發現系統一直被踢。

```gherkin
Scenario: 台股的上限是一條通道乘上每條五檔
  Given 台股方案為「同時一條通道、每條通道跟五檔」
  When 系統判定台股的同時跟盤上限
  Then 上限為五檔

Scenario: 兩條通道各跟三檔的上限是六檔
  Given 某市場方案為「同時兩條通道、每條通道跟三檔」
  When 系統判定該市場的同時跟盤上限
  Then 上限為六檔

Scenario: 一條通道只跟一檔的上限是一檔
  Given 某市場方案為「同時一條通道、每條通道跟一檔」
  When 系統判定該市場的同時跟盤上限
  Then 上限為一檔

Scenario: 不限通道數的市場不設上限
  Given 加密貨幣不限同時通道數
  When 系統判定加密貨幣的同時跟盤上限
  Then 不設上限，任何交易標的都跟得動
```

### US-02 — 一個市場的跟盤名單共用一條通道 [priority: P0]

**As a** 交易研究者，**I want** 名單上的每一檔共用一條通道，**so that** 系統不會因為多開通道被行情來源踢掉，我看的那一檔才拿得到穩定的即時更新。

```gherkin
Scenario: 四檔名單只開一條通道
  Given 台股方案為「同時一條通道、每條通道跟五檔」
  And 台股跟盤名單為四檔
  When 系統開始跟這份名單
  Then 系統只開一條即時通道
  And 這四檔全部掛在那一條通道上

Scenario: 只有一檔時走的是同一條路
  Given 台股跟盤名單只有一檔
  When 系統開始跟這份名單
  Then 系統開一條即時通道，上面掛著那一檔

Scenario: 名單為空時不開通道
  Given 現在是台股非交易時段，跟盤名單為空
  When 系統這一輪重新決定名單
  Then 系統不開任何即時通道

Scenario: 不限量的市場維持一檔一條
  Given 兩個不同的加密貨幣交易標的各有觀看者
  When 兩人開始看
  Then 系統為每一檔各開一條即時通道
```

### US-03 — 同一條通道上的每一檔各自收到自己的資料 [priority: P0]

**As a** 交易研究者，**I want** 共用通道不會讓不同股票的資料混在一起，**so that** 我看的那一檔就是我看的那一檔。

```gherkin
Scenario: 收到自己那一檔的進行中 K 線
  Given 交易標的甲與乙掛在同一條即時通道上
  And 某人正在看甲
  When 通道送來甲的進行中 K 線
  Then 看甲的人收到甲的那一根

Scenario: 收不到別人那一檔的資料
  Given 交易標的甲與乙掛在同一條即時通道上
  And 某人正在看甲
  When 通道送來乙的進行中 K 線
  Then 看甲的人收不到任何更新

Scenario: 走完的那一根只算在自己頭上
  Given 交易標的甲與乙掛在同一條即時通道上
  When 通道送來甲走完的那一根
  Then 甲的那一根被存入系統
  And 乙沒有任何 K 線被存入
```

### US-04 — 通道中斷時掛在上面的每一檔一起處理 [priority: P0]

**As a** 交易研究者，**I want** 通道斷掉時每一檔的觀看者都被告知，**so that** 沒有人盯著一張不會動、卻宣稱是即時的圖。

```gherkin
Scenario: 一條通道斷掉，上面每一檔的觀看者都被告知
  Given 交易標的甲、乙、丙掛在同一條即時通道上，三檔各有觀看者
  When 這條通道不再送來資料
  Then 甲、乙、丙的觀看者都被告知即時更新已停止

Scenario: 重新跟上時整份名單一起回來
  Given 一條掛著甲、乙、丙的通道已經中斷
  When 系統重新跟上並真的收到資料
  Then 系統開一條新的即時通道
  And 甲、乙、丙三檔全部掛在那條新通道上

Scenario: 連得上但不送資料，重試間隔照樣拉長
  Given 行情來源每次都接受連線，然後立刻中斷，從未送出任何資料
  When 系統連續重試
  Then 重試間隔逐次拉長，最長到三十秒
  And 不會固定停在最短的那一個間隔

Scenario: 真的收到資料才算恢復
  Given 一條通道重新連上並真的送來了一筆資料
  When 這條通道之後又中斷
  Then 下一次的重試間隔回到最短
```

### US-05 — 名單改變時通道重新建立 [priority: P1]

**As a** 交易研究者，**I want** 改動觀察清單之後，新的名單很快就跟得到，**so that** 我剛加進來的股票不必等到重開系統才有即時更新。

```gherkin
Scenario: 加入一檔會重建通道
  Given 一條即時通道上掛著甲與乙
  When 丙被加入觀察清單並取得名額
  Then 舊的通道先被結束
  And 系統再開一條新通道，上面掛著甲、乙、丙

Scenario: 移除一檔會重建通道
  Given 一條即時通道上掛著甲與乙
  When 乙被移出觀察清單
  Then 舊的通道先被結束
  And 系統再開一條新通道，上面只掛著甲

Scenario: 名單沒變就不動通道
  Given 一條即時通道上掛著甲與乙
  When 這一輪重新決定名單，結果仍是甲與乙
  Then 通道維持原樣，沒有任何一檔被中斷

Scenario: 名單變成空的就不再開通道
  Given 一條即時通道上掛著甲一檔
  When 甲被移出觀察清單，名單變成空的
  Then 舊的通道被結束
  And 系統不開新的通道

Scenario: 重建期間走完的那一根不會永久少掉
  Given 通道正在重建，這段期間沒有任何即時資料
  And 這段期間有一根 K 線走完
  When 下一輪自動抓取執行
  Then 那一根 K 線被取回並存入系統
```

## 4. Business Flow & Logic

### 核心業務規則

| # | 規則 |
| :--- | :--- |
| **R-01** | **即時通道**是系統與某個市場的行情來源之間、用來持續收取即時資料的一條連線。**一條通道可同時跟多檔。** |
| **R-02** | 一個市場的**同時通道數上限**與**每條通道跟盤檔數上限**都由該市場的行情來源方案決定，皆可調整、皆必須大於零。 |
| **R-03** | **同時跟盤上限**是推導值，等於「同時通道數上限 × 每條通道跟盤檔數上限」，**不可直接設定**。這樣人填不出一個方案不允許的值。 |
| **R-04** | 不限通道數的市場（加密貨幣）不設同時跟盤上限，且一條通道只跟一檔——維持現況。 |
| **R-05** | 跟盤名單的挑選規則完全不變：台股取觀察清單中**登錄最早**的那幾檔，至多同時跟盤上限，非交易時段名單為空。 |
| **R-06** | 名單決定之後，該市場的整份名單**掛上同一條即時通道**。名單有幾檔就跟幾檔，不去湊滿。 |
| **R-07** | 掛在同一條通道上的每一檔，**各自**收到自己的進行中 K 線與走完的 K 線；一檔的資料不會送給另一檔的觀看者。 |
| **R-08** | 通道不再送來資料時，**掛在它上面的每一檔**都被告知即時更新已停止，並由系統自行重新跟上**整條通道**。 |
| **R-09** | 重試間隔以**通道**為單位計算：逐次拉長、最長三十秒、不放棄；**只有真的收到資料**才讓間隔回到最短——連得上但不送資料不算恢復。 |
| **R-10** | 名單**改變時**整條通道重建：**先結束舊的，再開新的**。理由：方案只允許固定條數的通道，先開新的會在那一瞬間超限。名單**沒變**時通道不動。 |
| **R-11** | 通道重建期間的空窗由**每分鐘一輪的自動抓取**補上。即時跟盤是加值不是取代。 |
| **R-12** | 觀看者看到的內容不變：進行中 K 線、走完的 K 線、「即時更新已停止」的告知，形狀與時機都跟現在一樣。排在名額之外的觀看者一樣看得到圖，一樣被告知它沒有即時更新。 |

### Happy Path

1. 每一輪重新決定台股跟盤名單（R-05）。
2. 名單與目前通道上掛著的相同 → 什麼都不做（R-10）。
3. 名單不同 → 結束舊通道，開一條新通道，把整份名單掛上去（R-06、R-10）。
4. 通道送來資料 → 依交易標的分給各自的觀看者，走完的那一根存入（R-07）。
5. 通道中斷 → 每一檔的觀看者都被告知，系統依重試間隔重新跟上整條通道（R-08、R-09）。

### Edge Cases

| 情境 | 行為 |
| :--- | :--- |
| 名單為空（非交易時段、或觀察清單沒有台股） | 不開通道；已開的結束掉。 |
| 名單長度未達上限 | 有幾檔跟幾檔，不去湊滿。 |
| 通道連得上但從未送出資料 | 不算恢復，重試間隔照樣逐次拉長到三十秒。 |
| 通道中斷時名單上某一檔沒有任何觀看者 | 仍然重新跟上——台股的跟盤與有沒有人在看無關。 |
| 重建期間有 K 線走完 | 由每分鐘一輪的自動抓取補上。 |
| 行情來源完全不可用 | 其餘功能全部照常；查詢、指標計算、回測都不受影響。 |

## 6. Non-Functional Requirements

- **符合行情來源方案：** 台股在任一時刻同時開啟的即時通道數**不得超過方案允許的條數**（目前為一條）。這是本次最主要的非功能要求，也是整個切片存在的理由。
- **騷擾程度：** 一條連得上卻不送資料的通道，重試頻率最終降到每三十秒一次；改動前是每秒一次。
- **安全性：** 不涉及任何權限或身分規則的變更。
- **相容性：** 行情來源本來就支援「一條通道訂閱多檔」，取得方式與現在完全相同，不需要換方案、也不需要新的授權。

## 7. Dependencies & Risks

### External Dependencies

- **台股行情來源**：需支援單一連線上訂閱多檔（已確認支援），且其方案的通道數與訂閱數上限即為本切片的兩個設定值。

### Known Risks

| 風險 | 影響 | 因應 |
| :--- | :--- | :--- |
| 名單改變時整條通道重建，名單上其他檔也跟著中斷 | 觀察清單一改，所有名單內的股票都有一小段沒有即時更新 | 名單改變不頻繁（只在觀察清單被改動時）；空窗由每分鐘一輪的自動抓取補上，且觀看者會被明確告知，不會盯著一張假裝是即時的圖。 |
| 設定值填得比方案允許的大 | 仍會超限被踢 | 兩個設定值直接對應方案說明上的兩個數字，比舊的「上限五檔」更難填錯；且上限改為推導值，消除了「上限與通道數互相矛盾」這個狀態。 |
| 一條通道承載整份名單，它斷掉時影響範圍比以前大 | 以前斷一條只影響一檔 | 這是方案本身的形狀，不是選擇；而且改動前的實際狀態是「四條互相踢到全都不能用」，比集中在一條更糟。 |
