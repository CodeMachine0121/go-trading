# Product Requirements Document (PRD)

**Feature:** Telegram 投遞
**Status:** Draft
**Version:** v1.0
**Owner:** James Hsueh
**Stakeholders:** Engineering

---

## 1. Background & Goal (Why & Goal)

- **Problem Statement:**
  這個系統只在有人打開畫面問它的時候才說得出話。它算出來的每一件事——一次回測的成績、
  一支策略在某一棒給出的信號——都只在有人正好在看的時候存在。
  一位使用者要知道發生了什麼，唯一的辦法是自己回來看。
  **系統沒有任何一條主動說話的路。**

- **Expected Outcome:**
  鋪好第一條路，並當場證明它通。可驗證的結果有六項：
  1. 一位使用者留得下自己的 **Telegram 投遞設定**，且**每人最多一份**。
  2. 他打一則**測試訊息**，按下送出，**訊息真的出現在他的 Telegram 聊天室裡**。
  3. 送不出去時，系統說得出是**四種投遞失敗原因**的哪一種。
  4. 讀回設定時，**完整的機器人金鑰拿不回來**，只看得到**最後 4 個字**。
  5. 翻遍留存處，**找不到任何一串可以直接拿去用的機器人金鑰**。
  6. 系統**沒有拿到開鎖的東西時，寧可拒絕留存，也不會裸著存下去**。

- **Out of Scope:**
  - **自動把交易訊號、回測結果或任何系統事件送到 Telegram。**
    這一刀只鋪路與試通；沿著它送什麼、什麼時候送、誰決定送，是後面的切片。
  - 從 Telegram **收**訊息、讓人用 Telegram 對系統下指令。
  - Telegram 以外的投遞管道（電子郵件、Line、簡訊）。
  - 一位使用者設定**多個**聊天室或**多隻**機器人。
  - 送出紀錄的留存與查詢。
  - 送不出去時自動重試。
  - 測試訊息的頻率限制。

---

## 2. User Personas

- **Primary Role(s):** **使用者**——這台操作台的主人。他自己去 Telegram 開一隻機器人、
  自己知道要送到哪個聊天室，系統不代勞這兩件事。
- **Usage Context:**
  在瀏覽器上、已經登入的狀態下設定一次，然後按一顆鍵確認它通。
  設定完之後，他期待的是**「以後系統會主動找我」**，所以這一次試通要非常明確：
  通了就是通了，不通要說得出是哪一格填錯。

## 3. User Stories & Acceptance Criteria

### US-01 — 留下自己的 Telegram 投遞設定 [priority: P0]

**As a** 使用者，**I want** 留下我的機器人金鑰與聊天室代號，
**so that** 系統之後送得出訊息到我的 Telegram。

```gherkin
Scenario: 第一次設定
  Given 這位使用者還沒有任何 Telegram 投遞設定
  When 他以結尾為「1234」的機器人金鑰與聊天室代號「987654」完成設定
  Then 設定成功
  And 讀回來看到聊天室代號「987654」
  And 讀回來看到金鑰結尾「1234」

Scenario: 再設定一次是覆蓋，不是多一份
  Given 這位使用者已有一份設定，金鑰結尾是「1234」
  When 他以結尾為「5678」的金鑰再設定一次
  Then 他仍然只有一份設定
  And 讀回來看到金鑰結尾「5678」

Scenario: 金鑰不得為空白
  Given 使用者已經登入
  When 他以只有空白的機器人金鑰完成設定
  Then 設定被拒絕，並顯示「必須給一組機器人金鑰」

Scenario: 聊天室代號不得為空白
  Given 使用者已經登入
  When 他以只有空白的聊天室代號完成設定
  Then 設定被拒絕，並顯示「必須給一個聊天室代號」

Scenario: 前後空白不予保留
  Given 使用者已經登入
  When 他填入前後帶著空白的金鑰與聊天室代號
  Then 設定成功
  And 讀回來的聊天室代號沒有前後空白

Scenario: 沒有登入就設定不了
  Given 請求沒有帶著任何身分
  When 要求設定 Telegram 投遞
  Then 設定被拒絕，並顯示「請重新登入」
```

### US-02 — 金鑰設定之後拿不回來，也不裸著存 [priority: P0]

**As a** 使用者，**I want** 我的機器人金鑰在存進去之後就再也讀不回來，
**so that** 一個能把它讀回畫面的路，不會同時是一個能把它讀走的路。

```gherkin
Scenario: 讀回設定只看得到金鑰結尾
  Given 這位使用者已設定金鑰，結尾是「1234」
  When 他讀回自己的設定
  Then 他看到金鑰結尾「1234」
  And 回覆裡找不到完整的機器人金鑰

Scenario: 很短的金鑰仍然遮到拼不回去
  Given 這位使用者設定的金鑰整串只有 4 個字
  When 他讀回自己的設定
  Then 回覆裡看不到那 4 個字的完整內容

Scenario: 留存處沒有可以直接拿去用的金鑰
  Given 這位使用者已完成設定
  When 讀取系統為這份設定留下的內容
  Then 找不到那一串機器人金鑰的原文

Scenario: 系統開不了鎖時寧可拒絕
  Given 系統沒有拿到開鎖的東西
  When 使用者要求設定 Telegram 投遞
  Then 設定被拒絕，並顯示系統目前存不了機器人金鑰
  And 系統沒有以不上鎖的方式把金鑰存下去

Scenario: 還沒設定過不是錯誤
  Given 這位使用者還沒有任何設定
  When 他讀回自己的設定
  Then 系統回覆「還沒有設定」
  And 這不算一次失敗
```

### US-03 — 只碰得到自己的那一份 [priority: P0]

**As a** 使用者，**I want** 別人的 Telegram 設定我一概看不到也改不動，
**so that** 一把能冒充別人機器人說話的鑰匙，不會經過我這裡。

```gherkin
Scenario: 看不到別人的
  Given 甲已設定一份 Telegram 投遞設定
  And 乙還沒有設定
  When 乙讀回自己的設定
  Then 乙看到「還沒有設定」
  And 乙看不到甲的聊天室代號

Scenario: 改不動別人的
  Given 甲已設定一份，聊天室代號是「111」
  When 乙完成自己的設定，聊天室代號是「222」
  Then 甲那一份的聊天室代號仍然是「111」
  And 兩人各有各的一份
```

### US-04 — 送出一則測試訊息，當場知道通不通 [priority: P0]

**As a** 使用者，**I want** 打一句話按下送出，就看到它出現在我的 Telegram，
**so that** 我知道這條路真的通了，而不是等到系統第一次要通知我的時候才發現它不通。

```gherkin
Scenario: 送得出去
  Given 這位使用者已完成設定
  And Telegram 收下了這則訊息
  When 他送出「哈囉，這是一則測試」
  Then 系統回報送出成功

Scenario: 還沒設定就送不了
  Given 這位使用者還沒有任何設定
  When 他送出「哈囉」
  Then 送出被拒絕，並顯示要先完成 Telegram 設定

Scenario: 空白訊息被拒絕
  Given 這位使用者已完成設定
  When 他送出只有空白的訊息
  Then 送出被拒絕，並顯示「訊息不得為空白」

Scenario: 剛好 4096 個字元送得出去
  Given 這位使用者已完成設定
  When 他送出剛好 4096 個字元的訊息
  Then 系統回報送出成功

Scenario: 4097 個字元被拒絕而不是被截短
  Given 這位使用者已完成設定
  When 他送出 4097 個字元的訊息
  Then 送出被拒絕，並顯示超過一則訊息的上限 4096 個字元
  And 系統沒有把前 4096 個字元送出去

Scenario: 用的是存起來的那一份設定
  Given 這位使用者已設定聊天室代號「987654」
  When 他送出一則測試訊息
  Then 訊息被送往聊天室「987654」
```

### US-05 — 送不出去時，說得出是哪一種送不出去 [priority: P0]

**As a** 使用者，**I want** 送失敗時知道是哪一格填錯，
**so that** 我不必把兩格都重填一次來猜。

```gherkin
Scenario: 金鑰不被接受
  Given 這位使用者已完成設定
  And Telegram 表示這組機器人金鑰不被接受
  When 他送出一則測試訊息
  Then 系統回報金鑰不被接受，請重新設定機器人金鑰
  And 已存的設定原封不動

Scenario: 找不到這個聊天室
  Given 這位使用者已完成設定
  And Telegram 表示找不到這個聊天室
  When 他送出一則測試訊息
  Then 系統回報找不到這個聊天室，請確認聊天室代號
  And 已存的設定原封不動

Scenario: 連不上 Telegram
  Given 這位使用者已完成設定
  And Telegram 連不上
  When 他送出一則測試訊息
  Then 系統回報連不上 Telegram，請稍後再試
  And 已存的設定原封不動

Scenario: 等太久
  Given 這位使用者已完成設定
  And Telegram 遲遲不回答，超過等待上限
  When 他送出一則測試訊息
  Then 系統回報等太久，這則訊息當作沒送成
  And 已存的設定原封不動

Scenario: 四種原因彼此不同
  Given 這位使用者已完成設定
  When 他分別遇上金鑰不被接受、找不到聊天室、連不上、等太久
  Then 四次得到的說明各不相同
```

### US-06 — 整份移除 [priority: P1]

**As a** 使用者，**I want** 把自己的 Telegram 投遞設定整份拿掉，
**so that** 我不想再被系統找的時候，那把鑰匙就不留在它手上。

```gherkin
Scenario: 移除之後就送不出訊息
  Given 這位使用者已有一份設定
  When 他要求整份移除
  Then 移除成功
  And 他之後送測試訊息會被要求先完成設定

Scenario: 沒有設定的人要求移除也不算失敗
  Given 這位使用者沒有任何設定
  When 他要求整份移除
  Then 系統回報現在沒有設定
  And 這不算一次失敗

Scenario: 移除的是自己的
  Given 甲與乙各有一份設定
  When 甲要求整份移除
  Then 甲沒有設定了
  And 乙那一份仍然在
```

## 4. Business Flow & Logic

**Happy path（設定）**

1. 使用者帶著自己的身分，給出**機器人金鑰**與**聊天室代號**。
2. 系統認人；認不出來就到此為止。
3. 系統去掉兩者前後空白，判是否為空白。
4. 系統確認自己**拿得到開鎖的東西**；拿不到就拒絕整次設定。
5. 金鑰**上鎖**後與聊天室代號一起留存，覆蓋這位使用者原有的那一份（如果有）。
6. 回覆聊天室代號、金鑰結尾與設定時刻。

**Happy path（送出測試訊息）**

1. 使用者帶著自己的身分，給出一段**測試訊息**。
2. 系統認人；取出**他的**那一份設定，沒有就拒絕並說要先設定。
3. 去掉訊息前後空白，判空白與字數上限。
4. 把金鑰**開鎖**，以那隻機器人把訊息送到那個聊天室，**等待有上限**。
5. Telegram 收下就回報成功；否則回報**四種投遞失敗原因**之一。

**Core Business Rules**

- **R1 — 每人最多一份。** 再設定一次是覆蓋。
- **R2 — 只碰得到自己的。** 讀、寫、移除、送出，一律限於目前登入者自己那一份。
- **R3 — 金鑰是單向給出去的。** 進得去，出不來；讀回時只給**最後 4 個字**。
  **不存在任何一條把完整金鑰交回呼叫端的路。**
- **R4 — 金鑰上鎖留存，鑰匙不放旁邊。**
  它與密碼證明的差別要講清楚：密碼證明**算不回去**，因為系統不需要密碼本身；
  金鑰**必須讀得回來**才用得了，所以它只能被鎖起來。開鎖的東西不與留存處放在一起。
- **R5 — 開不了鎖就不存。** 系統沒拿到開鎖的東西時**拒絕整次設定**，
  並說明是系統存不了。**絕不退而求其次改用不上鎖的方式**——那樣設定會看起來成功、
  訊息也送得出去，只有被偷的那一天不一樣，而且沒有人會發現。
- **R6 — 聊天室代號不上鎖、照原樣顯示。** 它只說「送去哪」，光有它送不出任何東西；
  把它也遮起來，只會讓使用者看不出自己設錯了哪一個。
- **R7 — 送出用的是已存的那一份。** 不接受「這次先用這一組試試看」——
  那會多出一條「金鑰從外面進來、不經留存直接被拿去用」的路，而它與 R3 的方向相反。
- **R8 — 訊息超過上限是拒絕，不是截斷。** 理由與密碼上限相同：
  被截短的人不會知道自己送出去的是半則。
- **R9 — 四種投遞失敗原因不得合成一句。** 它們要人做的事完全不同。
- **R10 — 送不出去不改動已存的設定。** 一次沒送成可能只是 Telegram 那頭不在。
- **R11 — 移除一份不存在的設定不算失敗。** 目的已經達成。

**Edge Cases**

| 狀況 | 行為 |
| :--- | :--- |
| 使用者被刪除 | 他的 Telegram 投遞設定跟著不在——那把鑰匙不該比它的主人活得久 |
| 同一個人幾乎同時設定兩次 | 最後仍然只有一份，內容是其中一次的完整內容，不會是兩次混起來的 |
| 開鎖失敗（存進去時鎖得起來，現在開不了） | 送出失敗並說明是系統的問題，**不是**「金鑰不被接受」——使用者沒有東西可以改 |
| 對方從來沒有跟這隻機器人講過話 | 歸到**找不到這個聊天室**，而不是連不上——Telegram 不讓機器人主動私訊沒找過它的人，這是聊天室那一端的事，而且重試一百次也不會好。畫面因此要說「去按 Start」，不是「稍後再試」 |
| Telegram 回了一種系統沒見過的拒絕 | 歸到「連不上 Telegram，請稍後再試」 |
| 訊息裡有換行、表情符號、Telegram 會當成格式的符號 | 照使用者打的字面送出去，不做任何格式解讀——這是一則測試訊息，他要看的就是他打的那串 |
| 送出時剛好整份設定被移除 | 送出失敗並要求先完成設定 |

## 5. UI/UX Design & Interaction

本切片**不含畫面**，畫面在 `go-trading-frontend` 的 `2026-09-10-account-settings` 切片。
本切片對畫面的承諾：

- 「還沒有設定」是一個**正常狀態**，不是錯誤——畫面才畫得出空狀態。
- 讀回的設定一定帶得出**聊天室代號**與**金鑰結尾**，畫面才顯示得出「已設定，結尾 1234」。
- **四種投遞失敗原因彼此可分辨**，畫面才寫得出四句不同的話。
- 「系統目前存不了金鑰」與「你填錯了」是**兩種不同的拒絕**。

## 6. Non-Functional Requirements

- **Performance:**
  設定與讀取是一次留存處讀寫，即時。
  送出測試訊息要跑一趟外部服務，**有等待上限**（建議 10 秒等級，實際值於 architecture 決定）；
  等待期間不阻擋這位使用者的其他操作。
- **Security:**
  - **機器人金鑰是一把鑰匙，全程當鑰匙對待**：上鎖留存、只給結尾、不寫進紀錄檔、不回覆。
  - 開鎖的東西**不與留存處放在一起**；系統沒拿到它就拒絕留存（R5）。
  - 一位使用者只碰得到自己那一份（R2）。
  - Telegram 回來的原始說明可以轉達，但**不得夾帶金鑰**——外部服務的錯誤訊息有時會把
    請求原樣回貼，轉達之前要確認裡面沒有金鑰。
- **Compatibility:** 無額外要求。
- **Analytics / Tracking:** 不記錄訊息內容。

## 7. Dependencies & Risks

- **External Dependencies:**
  - **Telegram**：這是本系統第一個「會主動去找」的外部服務。它可能慢、可能不在、
    可能改變它的拒絕方式。系統對它的每一種回答都要有歸屬（見 Edge Cases 最後一列）。
- **Internal Dependencies:**
  - `2026-09-05-user-authentication`：目前登入者。
  - `2026-09-10-strategy-ownership-and-marketplace`：「只碰得到自己的東西」這條規則的既有寫法。
- **Known Risks:**
  - **開鎖的東西沒設定時，整個功能不能用。** 這是刻意的（R5），但它與登入簽章金鑰一樣，
    會在第一次部署時絆倒人。緩解：拒絕的那句話要**明說是哪一項系統設定沒給**。
  - **金鑰在紀錄檔裡漏出去**是最可能的實際外洩途徑，比留存處被偷更常見。
    實作時要把「不寫進紀錄檔」當成硬性要求，包含失敗路徑與外部服務的錯誤轉達。
  - **這一刀鋪的路，下一刀會自動沿著它送東西。** 屆時「一位使用者的設定壞掉」
    不能拖垮整輪自動投遞——這是下一個切片的事，但本切片的形狀要留得住那個可能。
