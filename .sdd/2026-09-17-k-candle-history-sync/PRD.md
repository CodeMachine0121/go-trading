## 1. Background & Goal (Why & Goal)

### Problem Statement

系統的兩條抓 K 線的路都不讓呼叫端說要多久：定時那一輪只抓最新的幾根；
補缺口抓到系統設定的回補上限為止，而且**刻意**不接受呼叫端指定。

所以「我要 BTCUSDT 最近三十天的一分鐘 K 線，現在」講不出來。唯一的辦法是改環境變數
再重啟，而那會連帶改變每一次自動回補的行為。

### Expected Outcome

- 一條新的路：**指名交易標的與回溯天數**，把那一段抓回來。
- 粒度固定一分鐘一根，不接受指定。
- **向來源問整段、但只寫沒有的**：既有的原封不動。問整段是唯一填得了中間破洞的問法——補缺口從「最新那根之後」開始，中間漏掉的永遠回不來。
- 回溯天數有上下限（1 到設定的上限，預設 90 天），超過即拒絕並說出上限。
- 回的報告與既有回補**一字不差**。

### Out of Scope

- 指定粒度、指定起訖時刻、非同步、前端、改動既有的 `POST /k-candles/backfill`。

## 2. User Personas

**Primary Role:** 系統的擁有者，拿 Postman 或 curl 直接打 API。

**Usage Context:** 他要測回測、要看一段歷史的圖，而系統手上沒有那段資料；
或是他懷疑某一段當初抓錯了，想重抓一次確認。**沒有畫面在等這支 API**。

## 3. User Stories & Acceptance Criteria

### US-01 — 指名一段歷史，現在就抓回來 [priority: P0]

**As a** 系統擁有者，**I want** 說出標的與回溯天數就把那段 K 線抓回來，
**so that** 我不必為了一次回測去改環境變數再重啟。

```gherkin
Scenario: 抓回指定的那一段
  Given BTCUSDT 已經登錄在系統裡
  And 系統裡一根 BTCUSDT 的 K 線都沒有
  When 我同步 BTCUSDT、回溯 30 天
  Then 那 30 天的一分鐘 K 線被抓回來並存下
  And 報告說出存了幾根

Scenario: 已經有的那幾根原封不動
  Given BTCUSDT 已經有最近 3 天的 K 線
  When 我同步 BTCUSDT、回溯 30 天
  Then 整整 30 天都向來源問過
  And 缺的那 27 天被補進去
  And 那 3 天一根都沒有被寫過

Scenario: 中間的破洞補得起來
  Given BTCUSDT 有第 1 天與第 30 天,中間 28 天是空的
  When 我同步 BTCUSDT、回溯 30 天
  Then 中間那 28 天補起來
  # 補缺口從「最新那根之後」開始,永遠回不到中間

Scenario: 本來就齊全的那一段什麼都不做
  Given 那 30 天本來就齊全
  When 我同步 BTCUSDT、回溯 30 天
  Then 報告說存了 0 根
  And 既有的一根都沒有被動到

Scenario: 粒度固定一分鐘
  Given BTCUSDT 已經登錄
  When 我看這一支的請求內容
  Then 沒有任何地方可以指定粗細
```

### US-02 — 說不通的要求被擋下來 [priority: P0]

**As a** 系統擁有者，**I want** 打錯的時候看得出來是哪裡錯，
**so that** 我不必自己一個個試。

```gherkin
Scenario: 沒登錄過的代號
  Given 系統沒有登錄過 FOOBAR
  When 我同步 FOOBAR、回溯 30 天
  Then 被拒絕,並說這個代號沒有登錄

Scenario: 代號空白
  When 我同步一個空白的代號
  Then 被拒絕,並說那不是一個代號

Scenario: 回溯天數超過上限
  Given 上限是 90 天
  When 我同步 BTCUSDT、回溯 91 天
  Then 被拒絕
  And 那句拒絕裡看得到 90

Scenario: 回溯天數不是正數
  When 我同步 BTCUSDT、回溯 0 天
  Then 被拒絕

Scenario: 沒給回溯天數
  When 我同步 BTCUSDT,不給回溯天數
  Then 被拒絕——這一支沒有預設值,說出要多久就是它的重點
```

### US-03 — 邊界上的那幾天照做 [priority: P1]

```gherkin
Scenario: 剛好一天
  Given 上限是 90 天
  When 我同步 BTCUSDT、回溯 1 天
  Then 照做

Scenario: 剛好是上限
  Given 上限是 90 天
  When 我同步 BTCUSDT、回溯 90 天
  Then 照做
```

### US-04 — 交代它做了什麼 [priority: P0]

**As a** 系統擁有者，**I want** 看得出哪幾根沒進去與為什麼，
**so that** 我知道那是資料的問題還是我要的東西本來就沒有。

```gherkin
Scenario: 報告與既有回補一字不差
  Given 抓回來的那批裡有一根違反了 K 線規則
  When 我同步
  Then 報告列出那一根與它違反了哪一條
  And 其餘照常存進去
  And 報告的形狀與 POST /k-candles/backfill 回的完全相同

Scenario: 市場那幾天沒開不算失敗
  Given 來源答了話,但那段期間市場沒有交易
  When 我同步
  Then 不算失敗
  And 報告說來源被問過了、存了 0 根

Scenario: 來源連不上
  Given 來源連不上
  When 我同步
  Then 回「稍後再試」那一類,不是「你寫錯了」那一類
```

## 4. Business Flow & Logic

### 一次歷史同步

```
POST /k-candles/history {symbol, lookbackDays}
  ├─ 代號說不通？        → 400
  ├─ 回溯天數說不通？    → 400（含超過上限，句子裡帶著上限）
  ├─ 代號沒登錄？        → 404
  │
  ├─ 放掉「這個市場今天休市」那個判斷（與既有手動回補同一條）
  ├─ 窗口 = 從「現在往回推 N 天、往下對齊」到「最後一根走完的一分鐘」
  │     **不以既有資料為起點** —— 整段重抓
  ├─ 向來源問（來源自己分頁）
  ├─ 逐根照既有 K 線規則判
  └─ **只寫沒有的**（同一個開盤時刻已經有資料就什麼都不做），回報告
```

### Core Business Rules

| # | Rule |
|---|------|
| BR-1 | 粒度固定一分鐘一根，請求裡沒有地方指定 |
| BR-2 | 窗口的起點**只由回溯天數決定**，不受既有資料影響——這是填得了中間破洞的唯一問法 |
| BR-2b | **寫的時候不覆蓋**：同一個開盤時刻已經有資料就什麼都不做。判斷交給資料庫，不是先讀再寫——兩個重疊的同步同時跑時，先讀再寫會雙雙認定不存在、雙雙寫下去 |
| BR-2c | 「存了幾根」講的是**這一次新增了幾根**；整段本來就齊全時它是 0 |
| BR-3 | 回溯天數必須是 1 到上限之間的整數；超過即拒絕並**說出上限** |
| BR-4 | 沒登錄過的代號拒絕；從代號長相猜市場是這個系統刻意不做的事 |
| BR-5 | **不推定休市**，也不因為推定過而略過——沿用既有手動回補 |
| BR-6 | 不碰觀察清單：不在清單上的標的照樣同步得動 |
| BR-7 | 報告的形狀與既有回補**完全相同** |

### 為什麼不是在既有那一支加一個欄位

`POST /k-candles/backfill` 的身分就是「回溯長度由系統決定」，那句話寫在它的請求物件上
當理由。加一個選填欄位會讓它變成半真的，而半真的規則比沒有規則更難維護。

### 為什麼問整段，卻不覆蓋

兩個決定，各有各的理由。

**問整段**，因為「從最新那根之後開始」已經有人做了，而且它補不到**中間的破洞**：
手上有第 1 天與第 30 天時，它從第 30 天之後開始，中間那 28 天再也回不來。

**不覆蓋**，因為要的是「把缺的補上」而不是「把抓錯的修掉」。不覆蓋還便宜：
已經齊全的那幾段不會被無謂地寫一次。修正抓錯的歷史是另一件事，
真的要做時與這一支的差別只有「寫的時候用哪一種」。

### Edge Cases

| 情境 | 行為 |
|------|------|
| 回溯天數是小數（例如 1.5） | JSON 解不進整數即 400 |
| 那段期間完全在市場休市內 | 不算失敗，存 0 根，報告說來源被問過 |
| 來源答了一半就斷 | 整次失敗回 502；已經存進去的留著（它們是對的） |
| 同一個標的連打兩次 | 第二次照樣向來源問整段，但一根都不會寫（都已經有了），報告說存了 0 根 |
| 九十天 | 約十三萬根、一百三十次來源往返，可能好幾分鐘 |

## 6. Non-Functional Requirements

- **同步回應**，不做成「先收下再問進度」：呼叫它的是 Postman 或一個人，沒有畫面在等，
  而那一套的複雜度是為了畫面上的等待而存在的。
- 上限由環境變數 `KCANDLE_HISTORY_SYNC_MAX_LOOKBACK_DAYS` 決定，預設 **90**；
  非正整數或讀不出來時退回預設。
- 一次同步整段候在記憶體裡再存。九十天約十三萬根——這就是上限存在的理由。

## 7. Dependencies & Risks

| 項目 | 說明 |
|------|------|
| 依賴 | `IMarketDataProxy`（既有，來源自己分頁）、`KCandleIngestionService` 的既有存入路徑 |
| 依賴 | 交易標的登錄（既有） |
| 風險 | 一次九十天要好幾分鐘，請求一直開著。以上限封頂；真的要更長時，該做的是「邊抓邊存」而不是把上限調高 |
| 風險 | 問整段會對來源打很多次，即使資料已經齊全。這是填得了破洞的代價；按的是手動工具，按的人知道自己在做什麼 |
