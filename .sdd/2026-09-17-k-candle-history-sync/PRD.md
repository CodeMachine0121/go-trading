## 1. Background & Goal (Why & Goal)

### Problem Statement

系統的兩條抓 K 線的路都不讓呼叫端說要多久：定時那一輪只抓最新的幾根；
補缺口抓到系統設定的回補上限為止，而且**刻意**不接受呼叫端指定。

所以「我要 BTCUSDT 最近三十天的一分鐘 K 線，現在」講不出來。唯一的辦法是改環境變數
再重啟，而那會連帶改變每一次自動回補的行為。

### Expected Outcome

- 一條新的路：**指名交易標的與回溯天數**，把那一段抓回來。
- 粒度固定一分鐘一根，不接受指定。
- **向來源問整段、但只寫沒有的**：既有的原封不動。問整段是唯一填得了中間破洞的問法——補缺口從「最新那根之後」開始，中間漏掉的永遠回不來。
- 回溯天數有上下限（1 到設定的上限，預設 3650 天＝十年），超過即拒絕並說出上限。
  那個上限是**防打錯字**，不是成本上限。
- **要抓得動四年**（約兩百萬根）：一天一段抓一段存一段、已經齊全的那幾段不問、
  照來源的節奏打。
- **不等抓完才回答**：回 `202` 與一筆歷史同步輪次，拿它的編號回來看進度。

### Out of Scope

- 指定粒度、指定起訖時刻、前端、改動既有的 `POST /k-candles/backfill`、
  取消一趟正在跑的同步。

## 2. User Personas

**Primary Role:** 系統的擁有者，拿 Postman 或 curl 直接打 API。

**Usage Context:** 他要測回測、要看一段歷史的圖，而系統手上沒有那段資料。
**沒有畫面在等這支 API**——但他也不會坐在終端機前面等十幾分鐘，
所以它回一筆輪次，他想起來的時候再回來看。

## 4. Business Flow & Logic

### 一次歷史同步

```
POST /k-candles/history {symbol, lookbackDays}
  ├─ 回溯天數說不通？    → 400（含超過上限，句子裡帶著上限）
  ├─ 代號說不通？        → 400
  ├─ 代號沒登錄？        → 404
  ├─ 放掉「這個市場今天休市」那個判斷（與既有手動回補同一條）
  ├─ 算出整段，切成一天一段
  ├─ 記下一筆歷史同步輪次（running，帶著總段數）；記不下來 → 502，什麼都不開始
  └─ 回 202 + 那筆輪次，抓取交給活得比這個請求久的東西

（背景）逐段走：
  ├─ 收進交易時段；空的就跳過
  ├─ 這一段手上已有的根數 == 這個市場那段時間開得出的根數？ → 連問都不問
  ├─ 照節奏向來源問這一段
  │     問不到 → 記下 fetchFailureReason，停掉剩下的段（不是失敗）
  ├─ 逐根照既有 K 線規則判
  ├─ **只寫沒有的**（同一個開盤時刻已經有資料就什麼都不做）
  │     寫不進去 → 輪次收在 failed
  └─ 更新輪次進度

GET /k-candles/history/{id}
  └─ 那筆輪次：status / completedChunks / totalChunks / storedCount / skippedCount
```

### Core Business Rules

| # | Rule |
|---|------|
| BR-1 | 粒度固定一分鐘一根，請求裡沒有地方指定 |
| BR-2 | 窗口的起點**只由回溯天數決定**，不受既有資料影響——這是填得了中間破洞的唯一問法 |
| BR-2b | **寫的時候不覆蓋**：同一個開盤時刻已經有資料就什麼都不做。判斷交給資料庫，不是先讀再寫——兩個重疊的同步同時跑時，先讀再寫會雙雙認定不存在、雙雙寫下去 |
| BR-2c | 「存了幾根」講的是**這一次新增了幾根**；整段本來就齊全時它是 0 |
| BR-3 | 回溯天數必須是 1 到上限之間的整數；超過即拒絕並**說出上限**。上限是**防打錯字**，不是成本上限 |
| BR-9 | 整段切成**一天一段**，**抓一段存一段**。不是效率調校：整段一次抓，四年約兩百萬根候在記憶體，而中途斷一次整趟白做 |
| BR-10 | 一段手上已有的根數達到那個市場在那段時間開得出的根數時，**連問都不問**。這是歷史同步唯一會看既有資料的地方，而且只決定「要不要問」，不決定「從哪裡開始」 |
| BR-11 | 某一段問不到時**停掉剩下的段**。剛剛拒絕一段的來源會用同樣方式拒絕接下來幾千段，硬打下去是把限流變成封鎖 |
| BR-12 | **先記輪次再回答**：POST 回 `202` 與輪次，抓取由活得比請求久的東西推動。輪次記不下來就整個請求拒絕 |
| BR-13 | 進度**以段數表示**（走到第幾段／共幾段），每走完一段就更新一次——只在收尾才出現的數字，跟卡住的分不出來 |
| BR-14 | 服務啟動時把還掛在 `running` 的輪次掃成 `failed`（`interrupted by restart`） |
| BR-15 | 每個行情來源都有**每分鐘請求數上限**，守在真正發出請求的地方——只有那裡知道一次呼叫會變成幾次。**一個來源一份**，所有打到它的 proxy 共用：額度是照來源算的，不是照問什麼問題算的 |
| BR-16 | **一個標的同時只跑一趟**歷史同步。第二趟回 `409` 並說出代號——那是有人按了兩次，不是故障。由資料庫決定（只蓋住 `running` 的唯一索引），不是先讀再寫 |
| BR-17 | 輪次的**收尾那一筆寫不進去要再試**。進度那幾筆不必——下一段馬上又寫一次；收尾那一筆是這趟最後會被說出來的話 |
| BR-18 | 收尾（含重啟掃殘留）一律**一併寫上收尾時間**。沒有收尾時間的 `failed` 讀起來像還在跑 |
| BR-19 | 收尾的段數是**它真正走到的那一段**，不是它被交代的總段數 |
| BR-4 | 沒登錄過的代號拒絕；從代號長相猜市場是這個系統刻意不做的事 |
| BR-5 | **不推定休市**，也不因為推定過而略過——沿用既有手動回補 |
| BR-6 | 不碰觀察清單：不在清單上的標的照樣同步得動 |
| BR-7 | 報告的形狀與既有回補**完全相同**——連「來源問不到寫進報告而不是整次失敗」這條也一樣 |
| BR-8 | **整次失敗只留給這個系統自己壞掉**（502）。一檔問不到是關於那一檔的事實，報告有一格專門講它 |

### 為什麼不是在既有那一支加一個欄位

`POST /k-candles/backfill` 的身分就是「回溯長度由系統決定」，那句話寫在它的請求物件上
當理由。加一個選填欄位會讓它變成半真的，而半真的規則比沒有規則更難維護。

### 為什麼問整段，卻不覆蓋

兩個決定，各有各的理由。

**問整段**，因為「從最新那根之後開始」已經有人做了，而且它補不到**中間的破洞**：
手上有第 1 天與第 30 天時，它從第 30 天之後開始，中間那 28 天再也回不來。

**不覆蓋**，因為要的是「把缺的補上」而不是「把抓錯的修掉」。不覆蓋還便宜：
已經齊全的那幾段不會被無謂地寫一次。修正抓錯的歷史是另一件事，
真的要做時與這一支的差別只有「寫的時候用哪一種」。

### Edge Cases

| 情境 | 行為 |
|------|------|
| 回溯天數是小數（例如 1.5） | JSON 解不進整數即 400 |
| 那段期間完全在市場休市內 | 不算失敗，存 0 根，報告說來源被問過 |
| 來源答了一半就斷 | 回 200，報告裡那一檔寫著 `fetchFailureReason`、`wasAsked` 為 false；已經存進去的留著（它們是對的）。整次失敗只留給**這個系統自己**壞掉 |
| 同一個標的連打兩次 | 第二次照樣向來源問整段，但一根都不會寫（都已經有了），報告說存了 0 根 |
| 四年 | 約兩百萬根、幾千次來源往返。幣安十來分鐘，一天答一次的台股來源更久。這正是它回輪次而不是回結果的理由 |
| 一段裡壞掉的根太多 | `skippedCount` 照實算，但列出來的名單有上限——一份沒人打得開的報告說的比短的少 |

## 6. Non-Functional Requirements

- **先收下再問進度**：POST 回 `202` 與輪次。四年是幾千次照節奏發出的請求，
  沒有哪一條連線值得開那麼久。
- 上限由環境變數 `KCANDLE_HISTORY_SYNC_MAX_LOOKBACK_DAYS` 決定，預設 **3650**；
  非正整數或讀不出來時退回預設。
- 記憶體用量與回溯天數**無關**：一次只握著一段。
- 來源節奏由 `MARKET_DATA_REQUESTS_PER_MINUTE`（預設 600）與
  `TAIWAN_STOCK_REQUESTS_PER_MINUTE`（預設 55）決定。

## 7. Dependencies & Risks

| 項目 | 說明 |
|------|------|
| 依賴 | `IMarketDataProxy`（既有，來源自己分頁）、`KCandleIngestionService` 的既有存入路徑 |
| 依賴 | 交易標的登錄（既有） |
| 風險 | 一趟四年要十幾分鐘到幾小時。以「先回輪次、背景抓、可查進度」處理，不靠上限 |
| 風險 | 來源額度。以每個來源自己的節奏上限處理，並留餘裕——那份額度是跟系統其他呼叫共用的 |
| 風險 | 問整段會對來源打很多次，即使資料已經齊全。這是填得了破洞的代價；按的是手動工具，按的人知道自己在做什麼 |
